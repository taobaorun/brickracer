brickracer · phase 1 · technical solution

让积木创作与实时竞速共用一套可信规则

推荐方案是纯客户端静态网页：React 管理儿童可理解的界面流程，独立的 Three.js + Rapier 运行时负责每帧渲染与物理，纯领域模块统一约束玩家搭建、AI 生成、积分和存档。

React UI shell Three.js WebGL2 Rapier WASM Web Audio localStorage V1 Playwright
核心取舍：赛车在物理上是一个聚合底盘，而不是每块积木一个刚体。普通积木仍影响受控的重量与重心；碰撞飞散只影响视觉，因此手机性能、比赛公平和赛后自动复原可以同时成立。

01

低频 UI / 高频游戏分离

React 不持有逐帧物理状态；运行时只发布节流 HUD 快照和无丢失结果事件。

02

一份蓝图，四处复用

同一验证器服务玩家搭建、AI 生成、存档加载和比赛入口，避免规则漂移。

03

静态客户端，无后端

账号、云同步和远程经济不进入一期；发布物可以由静态托管完整提供。

04

体验证据不能只靠自动化

真实手机负责 GPU、触控和音频；8–12 岁儿童观察测试负责独立可玩性。

boot → builder → race → results → shop
Player lifecycle

核心闭环如何穿过系统

每个跨界点都有一个明确权威：验证器决定能否参赛，比赛事实决定奖励，持久化事务决定能否写入。

01搭建触控/鼠标转换为网格命令
02验证连接、重叠、功能槽与范围
03编译车辆蓝图生成渲染实例与聚合物理
04实时比赛60 Hz 固定物理，30–60 Hz 呈现
05一次结算无丢失事件携带不可变比赛事实
06永久成长积分、解锁与新蓝图原子保存

搭建合法性

积木坐标是整数网格；连接图从不可拆底盘向外遍历。功能件只能安装到命名槽位。玩家、AI 和存档都不能绕过同一验证器。

  • 非法命令不改变权威蓝图
  • 比赛使用不可变蓝图快照
  • 积木质量与重心影响被约束

碰撞与复原

强碰撞隐藏部分装饰实例并生成短暂碎片；碎片不属于车辆碰撞组，也不进入积分和存档。离开比赛时所有实例复原。

  • 核心件永不成为碎片候选
  • 权威质量和性能保持不变
  • 碎片池有硬上限并统一释放
Decisions & tradeoffs

为什么选择这条路线

方案优先保护一期的辨识度、移动端性能和可验证性；不是为未来多人或无限内容预建平台。

维度采用未采用主要原因
3D 所有权独立 Three.js GameRuntimeReact Three Fiber 全场景让固定步物理与实例数据不受 React 重渲染生命周期影响。
车辆物理Rapier 动态刚体 + 射线车轮自制运动学移动保留碰撞、质量、抓地与悬挂，同时可通过参数实现街机容错。
积木物理单聚合车辆 + 视觉碎片逐积木刚体和关节降低移动端 bodies/contact 成本，并满足视觉脱落不改性能。
持久化版本化 localStorageIndexedDB / 后端一期数据很小；事件式写入、备份与版本冲突保护足够。
渲染基线WebGL2WebGPU-first覆盖当前目标浏览器，不为同一场景维护额外回退路径。
音频授权循环 + Web Audio 动态混音纯合成引擎声更接近可识别的发动机声浪，同时保留速度/油门联动。
Evidence contract

性能、恢复与验收

自动化证明规则和跨浏览器行为；物理手机与目标儿童负责自动化不能代替的证据。

≤16.7 ms桌面完整比赛 p95 帧时间目标
≤33.3 ms中端触屏手机完整比赛 p95 要求
≤8 s10 Mbps / 100 ms 冷启动至可交互搭建
0 次奖励重复、负积分或陈旧标签页静默覆盖
R1

桌面/触控浏览器闭环、真实 iOS/Android、冷启动与帧时间。

R2–R4

蓝图属性测试、搭建 E2E、控制车辆对照实验。

R5–R6

固定步车辆、复位、AI 合法性/评级分布与完整比赛。

R7–R8

音频解锁/静音、真人听测、碎片不改属性和赛后复原。

R9–R10

积分不变量、购买闭环、损坏/配额/多标签存档恢复。

R11

8–12 岁儿童无需外部说明完成完整闭环；必须由人类验收。

失败恢复

  • WebGL/WASM/资源失败可释放后重试
  • 比赛致命错误放弃未提交结果，不扣积分
  • 无效存档回退备份或安全默认
  • 旧标签页写入被拒绝并重载最新进度

明确延期

  • 多人、排行榜、分享和用户内容
  • 账号、云存档与跨设备同步
  • 更多赛道、赛道编辑和 PWA 离线
  • 分析平台、后台与商业化能力
